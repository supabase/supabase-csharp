# Migrating to 9.0.0

9.0.0 is not released yet. This guide lists the breaking changes planned for it as
they are decided, so that each deprecation in 8.x links to the change that replaces it.
Entries marked **Under consideration** are not decided yet.

All packages are versioned in lockstep, so this major bump applies to every
`Supabase.*` package at once.

## 1. Gotrue: `ResetPasswordForEmailOptions.PKCEVerifier` removed

**Why:** the SDK never reads this property. With `FlowType = OAuthFlowType.PKCE`,
`ResetPasswordForEmail(ResetPasswordForEmailOptions)` generates a new code verifier,
sends its challenge, and returns the verifier on
`ResetPasswordForEmailState.PKCEVerifier`. Setting the option did nothing. It is
marked `[Obsolete]` in 8.x.

**What you need to do:** stop setting the option. Read the verifier from the
returned state and keep it until you call `ExchangeCodeForSession`:

```csharp
// Before: the assignment has no effect
var options = new ResetPasswordForEmailOptions(email)
{
    FlowType = OAuthFlowType.PKCE,
    PKCEVerifier = myVerifier,
};
await client.Auth.ResetPasswordForEmail(options);

// After: the SDK generates the verifier and returns it
var state = await client.Auth.ResetPasswordForEmail(
    new ResetPasswordForEmailOptions(email) { FlowType = OAuthFlowType.PKCE });
var verifier = state.PKCEVerifier;
```

## 2. Gotrue: `SignUpOptions` no longer derives from `SignInOptions`

**Why:** `SignUpOptions` inherits `Scopes` and `QueryParams` from `SignInOptions`.
Those two properties configure the OAuth authorize URL that `SignIn(Provider, SignInOptions)`
builds. Neither `SignUp` overload reads them, so setting them on a sign-up has no
effect. In 9.0.0, `SignUpOptions` is a separate type that has only the members
sign-up uses.

**What you need to do:**

- Remove any assignment to `Scopes` or `QueryParams` on a `SignUpOptions`. They were
  never sent.
- If you passed a `SignUpOptions` instance where a `SignInOptions` is expected, such
  as `SignIn(Provider, SignInOptions)`, `SendMagicLink` or `LinkIdentity`, create a
  `SignInOptions` for that call instead.

## 3. Gotrue: sign-in raises `SignedIn` without a preceding `UserUpdated`

**Under consideration.**

**Why:** in 8.x, storing a new session raises `UserUpdated`, and the sign-in
method then raises `SignedIn`. A listener therefore receives `UserUpdated` followed by
`SignedIn` for a single sign-in. This happens with the email and phone password
sign-ins, `SignInWithIdToken`, `SignInAnonymously`, `VerifyOTP`, `VerifyTokenHash`,
`ExchangeCodeForSession`, `SignInWithPasskeyAsync`, `LinkIdentityWithIdToken`,
`GetSessionFromUrl` (when it stores the session), and `SignUp` when it returns a
session. MFA verification follows the same pattern: `UserUpdated` and then
`MfaChallengeVerified`. `SetSession` already raises `SignedIn` alone. supabase-js
raises only `SIGNED_IN` on sign-in and keeps `USER_UPDATED` for changes to an
existing user, such as `updateUser`.

**What you would need to do:** no source change, and nothing fails at compile
time. A listener that relies on `UserUpdated` to learn that a user signed in must
also handle `SignedIn` (and `MfaChallengeVerified` after MFA verification).

## 4. Gotrue: `IGotrueClient.SignUp` removed in favor of `SignUpAsync`

Both `SignUp(string email, string password, SignUpOptions? options)` and
`SignUp(SignUpType type, string identifier, string password, SignUpOptions? options)` are
`[Obsolete]` since 8.x and are removed in 9.0.0.

**Why:** `SignUp` returns a `Session?` that means two different things: a signed-in session when
the project does not require confirmation, and a token-less carrier of the pending user when it
does. It also ignores `SignUpOptions.FlowType` and `SignUpOptions.Channel`, so a PKCE email
sign-up sent no code challenge and a phone sign-up could not choose WhatsApp. `SignUpAsync`
returns a `SignUpState` that keeps those cases apart, honors both options, and takes a
`CancellationToken`.

**What you need to do:**

```csharp
// Before
var session = await client.SignUp(email, password);
var signedIn = session?.AccessToken != null;

// After
var signedUp = await client.SignUpAsync(SignUpType.Email, email, password);
var signedIn = signedUp.Session != null;
var user = signedUp.User;
var verifier = signedUp.PKCEVerifier;
```

- `signedUp.Session` is the session the user is signed in with, or `null` while they still have to
  confirm. The client adopts it, persists it and raises `SignedIn`, as `SignUp` did.
- `signedUp.User` is the signed-up user, including one awaiting confirmation.
- `signedUp.PKCEVerifier` is set for an email sign-up with `FlowType = OAuthFlowType.PKCE`. Pass it
  with the code from the confirmation link to `ExchangeCodeForSession`.
