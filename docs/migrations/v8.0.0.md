# Migrating to 8.0.0

This guide covers the breaking changes in 8.0.0 and what you need to do about them.
For the full list of every change, see [`CHANGELOG.md`](../../CHANGELOG.md).

All packages are versioned in lockstep, so this major bump applies to every
`Supabase.*` package at once.

## 1. Parameterless `Table.Delete(...)` now returns the deleted rows

`IPostgrestTable.Delete(QueryOptions?, CancellationToken)` (and its `Table`
implementation) now returns `Task<ModeledResponse<TModel>>` instead of `Task`.

**Why:** a delete that is blocked by a row-level-security policy, or that matches no
rows, is not an error in PostgREST — the request succeeds and returns an empty
representation. The old signature discarded the response body, so callers could not
tell "nothing was deleted" apart from "deleted" and saw a phantom success
([#334](https://github.com/supabase-community/supabase-csharp/issues/334)). The rows
were already on the wire (`QueryOptions.Returning` defaults to `Representation`); the
method now hands them back. The SDK still does not throw on an empty delete — you
decide how to react.

**What you need to do:**

- If you already `await` the call and ignore the result, no source change is needed —
  but you must recompile against 8.0.0.
- If you assigned the result to a `Task`, or captured the method group as a `Func<Task>`
  / delegate, update the type to `Task<ModeledResponse<TModel>>`.
- To act on whether anything was actually deleted, inspect `Models`:

```csharp
// Before (8.0.0 removes this shape — the deleted rows were unavailable)
await client.Table<Todo>()
    .Filter("id", Operator.Equals, "1")
    .Delete();

// After — the deleted rows come back in Models
var response = await client.Table<Todo>()
    .Filter("id", Operator.Equals, "1")
    .Delete();

if (response.Models.Count == 0)
{
    // Nothing was deleted: the row did not exist, or an RLS policy hid it.
    // Decide how to react.
}
```

The `Delete(TModel model, ...)` overload is unchanged — it already returned
`Task<ModeledResponse<TModel>>`.

## 2. Newtonsoft.Json replaced with System.Text.Json

The SDK now uses `System.Text.Json` instead of `Newtonsoft.Json` for all serialization.

**Why:** `System.Text.Json` is built into the .NET runtime, reducing external
dependencies and enabling trimming / ahead-of-time (AOT) compilation — important
for cloud-native workloads. Performance is also significantly better.

**What this means for you:**

If you use the SDK to query models and only interact with types like
`Client.Table<T>()`, `Auth`, `Realtime`, and `Storage`, **no changes are needed** —
the SDK handles serialization internally, and the wire format is unchanged.

If you have custom code that does any of the following, read the sections below:

- Define your own model classes with JSON attributes
- Call `JsonConvert.Serialize/Deserialize` directly
- Pass custom serialization options or converters to the SDK

### Custom models with JSON attributes

If your project defines model classes with `[JsonProperty]` from Newtonsoft.Json:

```csharp
// Before (Newtonsoft.Json) — no longer works
using Newtonsoft.Json;

[JsonObject(MemberSerialization = MemberSerialization.OptIn)]
public class MyModel
{
    [JsonProperty("user_id")]
    public int UserId { get; set; }
}

// After (System.Text.Json) — update to this
using System.Text.Json.Serialization;

public class MyModel
{
    [JsonPropertyName("user_id")]
    public int UserId { get; set; }
}
```

Key changes:

- Replace `using Newtonsoft.Json;` with `using System.Text.Json.Serialization;`
- Replace `[JsonProperty("name")]` with `[JsonPropertyName("name")]`
- Remove `[JsonObject(...)]` declarations; System.Text.Json opt-in is less common
- If you were using `[JsonIgnore]`, it still exists — no change needed
- For `NullValueHandling`, use `[JsonIgnore(Condition = JsonIgnoreCondition.WhenWritingNull)]` instead

### Direct serialization calls

If you serialize or deserialize JSON manually in your own code:

```csharp
// Before (Newtonsoft.Json) — no longer works
using Newtonsoft.Json;
var json = JsonConvert.SerializeObject(obj);
var obj = JsonConvert.DeserializeObject<MyModel>(json);

// After (System.Text.Json) — update to this
using System.Text.Json;
var json = JsonSerializer.Serialize(obj);
var obj = JsonSerializer.Deserialize<MyModel>(json);
```

For most cases, `JsonSerializer` is drop-in compatible. If you were relying on
Newtonsoft-specific behavior (like lenient string-to-number coercion), you may
need to create a `JsonSerializerOptions` with `NumberHandling = JsonNumberHandling.AllowReadingFromString`.

### Serialization options passed to the SDK

If you were creating or modifying `JsonSerializerSettings` before passing them
to the SDK, update to `JsonSerializerOptions` from `System.Text.Json.Serialization`:

```csharp
// Before (Newtonsoft.Json)
var settings = new JsonSerializerSettings { NullValueHandling = NullValueHandling.Ignore };

// After (System.Text.Json)
var options = new JsonSerializerOptions { DefaultIgnoreCondition = JsonIgnoreCondition.WhenWritingNull };
```

The SDK's public option types (e.g., `ClientOptions`, `PostgrestOptions`) remain
unchanged in shape — they still take serialization options where applicable, just
with the new STJ types under the hood.

## 3. Packages retarget to .NET Standard 2.1

Every shipped package now targets `netstandard2.1` (previously `netstandard2.0`).

**Why:** `netstandard2.1` unlocks newer runtime APIs and lets the SDK drop
compatibility shims.

**What you need to do:**

- If your project runs on **.NET Core 3.0+, .NET 5+, .NET 8/10, or a recent
  MAUI / Mono 6.4+ / Xamarin target**, you already satisfy `netstandard2.1` — no
  change is needed.
- If you target **.NET Framework** (any version — `netstandard2.0` is its ceiling)
  or a **pre-`netstandard2.1` runtime** (Mono < 6.4, older Xamarin/Unity), you can no
  longer reference these packages. Move to a `netstandard2.1`-capable target, for
  example by migrating the consuming project from .NET Framework to .NET 8+.

## 4. Gotrue: `NetworkStatus.PingCheck` renamed to `PingCheckAsync`

**Why:** the method was already asynchronous but didn't carry the `Async` suffix;
renamed while the file was already being touched for this release, matching the
convention applied elsewhere in the 8.0.0 migration.

**What you need to do:**

```csharp
// Before
var isOnline = await networkStatus.PingCheck(url);

// After
var isOnline = await networkStatus.PingCheckAsync(url);
```

## 5. `Table.Single(...)` now throws when more than one row matches

`Single()` still returns `null` for zero rows and the model for exactly one row, but a
query that matches **more than one row** now throws a `PostgrestException` instead of
returning `null`.

**Why:** the old implementation asked PostgREST for a single object
(`Accept: application/vnd.pgrst.object+json`), which answers *both* "zero rows" and
"several rows" with the same `406 Not Acceptable`. The catch that turned that 406 into
`null` therefore could not tell the two apart, so an under-constrained query — one your
filters failed to narrow to a single row — silently returned `null` and looked exactly
like "not found" ([#300](https://github.com/supabase-community/supabase-csharp/issues/300)).
`Single()` now fetches the list and enforces the cardinality client-side (as
postgrest-js's `maybeSingle()` does): zero rows → `null`, one row → the model, more than
one row → an exception.

**What you need to do:**

- If your filters always identify at most one row (for example, filtering on a primary
  key or a unique column), nothing changes — you never hit the multi-row path.
- If you previously relied on a multi-row match coming back as `null`, that no longer
  happens; catch the exception (or tighten the query so it can only match one row):

```csharp
// Before (7.x) — a query matching several rows returned null, indistinguishable from "not found"
var todo = await client.Table<Todo>()
    .Filter("name", Operator.Equals, "walk the dog")
    .Single();

if (todo is null)
{
    // Could mean "no match" OR "more than one match" — you couldn't tell.
}

// After (8.0.0) — more than one match throws; null now means "no match" unambiguously
try
{
    var todo = await client.Table<Todo>()
        .Filter("name", Operator.Equals, "walk the dog")
        .Single();

    if (todo is null)
    {
        // Exactly zero rows matched.
    }
}
catch (PostgrestException ex)
{
    // More than one row matched — the filter didn't narrow to a single row.
    // Message: "The query matched N rows when at most one was expected."
}
```

The thrown `PostgrestException` carries `StatusCode` `406` (`Not Acceptable`), preserving
the status the old single-object request returned for the same condition.

## 6. Realtime: registering `postgres_changes` after `Subscribe()` now throws

Registering a `postgres_changes` listener on a channel that has already joined (or is in
the middle of joining) now throws a `RealtimeException`. This affects
`Channel.OnPostgresChange(...)` and `Client.On(...)` / `Channel.Register(...)` — any path
that adds a `postgres_changes` binding after `Subscribe()` has been called.

**Why:** the set of `postgres_changes` bindings is sent to the server as part of the
channel join. Adding another one afterward never took effect — the server had already been
told which changes to stream, so the late listener silently received nothing
([#385](https://github.com/supabase-community/supabase-csharp/issues/385)). The SDK now
fails fast with an explanatory exception instead of registering a callback that can never
fire.

**What you need to do:**

- Register every `postgres_changes` listener **before** calling `Subscribe()`. If your code
  already does this — the documented and common pattern — nothing changes.
- If you added listeners after subscribing, move those calls ahead of `Subscribe()`. If you
  need a different set of changes later, create a new channel for them.

```csharp
// Before (7.x) — the second listener was accepted but never fired
var channel = client.Realtime.Channel("public", "todos");
channel.OnPostgresChange(OnInsert, ListenType.Inserts);
await channel.Subscribe();
channel.OnPostgresChange(OnUpdate, ListenType.Updates); // silently ignored

// After (8.0.0) — register all listeners first
var channel = client.Realtime.Channel("public", "todos");
channel.OnPostgresChange(OnInsert, ListenType.Inserts);
channel.OnPostgresChange(OnUpdate, ListenType.Updates);
await channel.Subscribe();
```

The thrown `RealtimeException` carries `Reason` `FailureHint.Reason.StateInvalid` and a
message of the form `Cannot add `postgres_changes` callbacks for {topic} after `Subscribe()`.`

## 7. Gotrue: OAuth `state` parameter removed

`SignInOptions.State` and `ProviderAuthState.State` have been removed, and the SDK no longer
adds a `state` query parameter to the provider authorize URL.

**Why:** the OAuth `state` for a Supabase provider flow is generated and validated by the
GoTrue server (its `flow_state`), not by the client. Sending our own `state` collided with
that round-trip and made social sign-in (Google, Apple, …) fail on the callback with
`error_code=bad_oauth_state`
([#377](https://github.com/supabase-community/supabase-csharp/issues/377)). Supabase's own
`auth-js` SDK does not send a `state` either. The property was added in 6.1.0 and never
worked as intended — nothing validated it — so it is being removed rather than deprecated.

**What you need to do:**

- Remove any use of `SignInOptions.State` and `ProviderAuthState.State`. If you set `State`,
  simply delete it — sign-in now works without it.
- If you were relying on `state` for server-side CSRF correlation (the original goal of
  [#222](https://github.com/supabase-community/supabase-csharp/issues/222)), carry your own
  token on `RedirectTo` instead. GoTrue preserves the `redirect_to` query string and echoes
  it back to your callback, so you can validate it there. The PKCE `code_verifier` returned
  as `ProviderAuthState.PKCEVerifier` remains available for server-side storage.

```csharp
// Before (6.1.0–7.x) — broke social sign-in with bad_oauth_state
var auth = await client.SignIn(Provider.Google, new SignInOptions
{
    FlowType = OAuthFlowType.PKCE,
    State    = myCsrfToken, // removed
});

// After (8.0.0) — carry correlation state on redirect_to; GoTrue echoes it back
var auth = await client.SignIn(Provider.Google, new SignInOptions
{
    FlowType   = OAuthFlowType.PKCE,
    RedirectTo = $"https://myapp.com/callback?csrf={myCsrfToken}",
});
// On the callback, validate the `csrf` query param, then exchange the code:
// await client.ExchangeCodeForSession(storedPkceVerifier, code);
```

## 8. Gotrue: a failed token refresh no longer signs the user out

**Why:** `RetrieveSessionAsync` destroyed the session on any refresh failure, so
starting an app without connectivity wiped the persisted session and forced a new
login ([#390](https://github.com/supabase-community/supabase-csharp/issues/390)). Now only a rejection the server reports as an invalid refresh token
signs the user out; a network error, timeout or 5xx keeps the session so the
next refresh can retry. For the same reason the method returns the loaded
session instead of throwing when the client is marked offline.

**What you need to do:** nothing, unless you relied on a `null` return, the
thrown offline exception, or the `SignedOut` event to detect a failed refresh:
a returned session is no longer a guarantee that its access token is still
valid.
